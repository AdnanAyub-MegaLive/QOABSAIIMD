Database Management — destructive maintenance

Route: /database-management. API: /api/admin/database-management.
Only the active SUPER_ADMIN whose email matches ADMIN_EMAIL may access it.
This is not a delegable permission. It is available in both dev and production.

No existing application data was deleted during implementation. Deletion is gated by
DATABASE_MANAGEMENT_DELETE_ENABLED=true, intentionally unset by this change.
The service has been verified against the full schema in a disposable PostgreSQL
18 database on a separate temporary cluster. Restart after configuring it.
Preview works without enabling it; this change does not enable production deletion.

Choose one exact id/publicId, a whole table, or all public application tables.
Review counts of ALL foreign-key dependants. Relationships may connect other
users: these are included, even SET NULL relations. Confirm the exact phrase
and current admin password. A signed preview expires after five minutes and
is rejected if affected row locations/transaction versions changed. Writers are
blocked during execution; plan for a maintenance window. Max 100,000 rows.

Admin and _prisma_migrations are protected. No deletion audit, tombstone, ledger
reversal or archive is created. DELETE statements execute in one transaction;
any failure rolls back the whole operation. All ordinary archive controls are
unchanged. This feature does not perform refunds or recalculate other balances.

Reference scanning also follows nested JSON, arrays, object keys, identifier
fields and delimited IDs in text/URLs/channels. Matching records appear in the
preview and their own FK dependants are included. Substring matches and ordinary
numeric amounts do not count; numeric IDs require typed/contextual references.
It does not infer identity from a display name, encrypted/compressed blob, or
unrecorded historical alias. Whole-data reset clears public application
tables but preserves administrator accounts and migration metadata. Custom
triggers and cross-schema dependencies cause execution to refuse safely.
Backups/WAL, CDN/object storage, files, process caches and phone caches are not
purged. An already sent message or downloaded file cannot be recalled here.

Validation performed: unit tests plus full-schema isolated PostgreSQL integration:
read-only preview, stale-plan rollback, device/prop/ledger removal, JSON/text
cleanup, unrelated user balance and shared-asset preservation, complete data
reset, protected administrator survival. Disposable database was dropped after
each run. No Docker was used. Use a maintenance window with background writers paused: workers can
otherwise recreate default records after a reset. Deleted users' sockets are
disconnected best-effort after commit.
