1. Executive Summary

The Streamline Administration Portal was started as a new administrative backend for a combined video and audio streaming application, comparable in operating model to platforms such as StreamKar and OyeTalk. The mobile application is being developed separately in React Native CLI; this portal provides the operational interface, persistent data layer, mobile APIs and real-time controls required by administrators.

The work progressed from an initial administrator login screen into a multi-module system covering users/senders, hosts, audio rooms, agencies, content uploads, bans, devices, virtual currency, special IDs and audit logs. PostgreSQL and Prisma now store the principal records, NextAuth protects administrative access, and Socket.IO communicates immediate account and room events to the mobile application.

At the end of this reporting period, the portal has a working technical foundation and several operationally functional modules. Some business modules—particularly the deeper agency workflows, live-stream operations and reporting—remain UI-ready or planned and require final rules, integrations and production data.

Core database coverage

The schema contains 20 models, including administrators, audit logs, users, hosts, devices, gifts, coin adjustments, bans, verification, salaries, albums, special IDs, game logs, live sessions, performance, violations, audio rooms and upload assignments. Relationships and indexes were added for common searches such as user status, VIP level, device MAC address, ban expiry, room state and assignment expiry.

Security approach

  • Passwords are stored as hashes rather than recoverable plain text.
  • Administrators can reset a user password and receive a generated temporary password; the reset increments the session version and forces active sessions to log out.
  • Soft deletion preserves operational history while removing login capability and personal account identifiers.
  • Administrative actions are recorded with administrator, entity, reason, metadata and timestamp.
  • Signed upload URLs are bound to the user and session version and expire after a limited period.

5. Key Business Workflows

User lifecycle

  1. A user registers through the mobile API using a unique phone number; email is optional and cannot be duplicated.
  2. Login validates credentials, account status and the current device before issuing a session.
  3. Administrators can manage roles, VIP status, coins, special IDs, bans, password reset and account deletion.
  4. Every sensitive administrative action is written to the audit log and relevant real-time events are sent to the app.

Time-based control model

A common minute-based duration system is used throughout the portal. Administrators can select predefined periods or enter custom minutes, while the UI displays the calculated human-readable value. The approach is used for bans, special IDs, room controls and uploaded-asset grants.

Upload and entitlement workflow

  1. An administrator uploads an image, GIF, WebP or supported video into one of eight content categories.
  2. The asset stores a title, details, tags, file metadata, media bytes and room-background eligibility.
  3. The asset may be global or granted to multiple users. Each user grant has an independent duration and expiry.
  4. Only global or actively granted assets appear in the mobile catalogue. Expired access is also rejected by the file endpoint.
  5. Assigned items are displayed in the relevant user’s dedicated portal profile.

Audio-room lifecycle

  1. The system assigns a persistent room ID to a room owner.
  2. When the room becomes empty, live resources are released and the room becomes idle, but its ID remains attached to the owner.
  3. When the owner starts again, the same ID is reactivated.
  4. Administrators can disable joining, block or terminate the room for a set time, then manually restore it or allow automatic expiry.

8. Current Status, Gaps and Risks

Operationally functional

  • Admin authentication, navigation and global feature search.
  • Core user records, mobile registration/login/profile/session APIs and device capture.
  • Security actions, automated expiry, force logout and audit logging.
  • Persistent audio-room identity, discovery and Socket.IO coordination.
  • Database-backed upload catalogue, signed media delivery and timed multi-user entitlements.

UI-ready or partially populated

  • Several supporting user/host tables use representative or seed data until the mobile application sends all corresponding records.
  • Agency ranking, tasks, salary and application tabs are designed but require final database entities, business rules and workflows.
  • Audio recording and permanent room deletion code are intentionally not exposed in the interface.
  • Live-stream management and formal reporting navigation are placeholders for a later phase.

Risks requiring management decisions

Infrastructure: Media is currently stored inside PostgreSQL. This is suitable for controlled development and early testing, but object storage/CDN should be adopted before high-volume production use.
Mobile media origins: Physical devices cannot use the backend’s localhost address. Production requires a stable HTTPS API/media hostname and configured mobile CORS origin.
Permissions: The portal currently has administrator authentication, but granular role-based access control should be finalized for Super Admin, finance, moderation, content and support teams.
Testing: Lint and production builds pass, but automated integration, end-to-end, load and security testing should be added before production launch.

9. Recommended Next Phase

  1. Finalize business requirements: confirm agency commission formulas, host salary calculations, moderation policies, reporting KPIs and admin permission levels.
  2. Complete remaining database modules: convert remaining representative tables and agency workflows to live database records and mobile event ingestion.
  3. Production media architecture: move uploaded media to S3-compatible object storage with CDN delivery, virus/type validation and image/video processing.
  4. Production security: add granular RBAC, rate limiting, login throttling, secret rotation, HTTPS-only cookies/tokens and formal audit retention.
  5. Quality assurance: create API contract tests, database integration tests, Socket.IO tests and browser/mobile end-to-end scenarios.
  6. Deployment and monitoring: establish staging/production environments, managed PostgreSQL, backups, error monitoring, uptime alerts and structured logs.
  7. Mobile integration sign-off: jointly validate registration, login, bans, force logout, room discovery, seats and assigned media on physical Android/iOS devices.

Management conclusion

The portal has moved well beyond a visual prototype. It now provides a connected administrative foundation with persistent data, secure session control, mobile APIs and real-time operational actions. The most important next step is to convert the remaining business placeholders into approved production workflows, strengthen infrastructure and security, and execute formal end-to-end testing with the React Native application.
